# First Run appliance

`beam-appliance-firstboot.service` owns `tty1` while
`/var/lib/beam-appliance/firstboot-complete` is absent. It starts a dedicated
local Xorg server through `xinit`, then runs the root-owned Tkinter wizard as its
only client. Xorg listens on no TCP socket, LightDM is not involved, XFCE is not
started and no shell is exposed. Once the atomic marker exists,
`beam-appliance-status.service` owns `tty1` as `beammanager`; local maintenance
login remains available on `tty2` with `Alt+F2`.

The First Run service is pulled directly by `sysinit.target`, uses
`DefaultDependencies=no`, and waits only for local filesystems, tmpfiles and the
initial keyboard setup. It selects VT1 itself before starting Python. It has no
ordering or requirement relationship with Manager, networking, getty,
`multi-user.target`, `graphical.target`, LightDM or Plymouth. The interactive
process is `Type=simple`, so normal boot may continue concurrently after the
wizard process has started.

The default UX is a dark, full-screen, mouse-and-keyboard interface with Beam
green accents. It exposes only human country, keyboard and city labels; locale,
XKB identifiers and IANA timezones remain internal allowlisted values. The
existing console workflow remains available solely as the explicit maintenance
fallback `beam-appliance-firstboot --text`.

First Run and permanent status use inverse marker conditions and do not declare
a mutual `Conflicts=` relationship. This is intentional: systemd resolves job
conflicts before it evaluates conditions, so mutually conflicting units wanted
by the same boot transaction can both be discarded. `getty@tty1` remains masked;
`getty@tty2` provides local maintenance. LightDM/display-manager receives a
positive marker-gated drop-in, so its graphical greeter cannot appear on an
unfinished appliance. A graphical-target oneshot returns the visible VT to tty1
after a completed boot while XFCE remains installed for Gate 3.

Plymouth has no product role. Its boot services are masked and the kernel command
line includes `plymouth.enable=0`; the package is not purged in Gate 3 to avoid an
unrelated XFCE package-graph change. UFW remains at `logging low`, while the
kernel console level prevents warning-level firewall messages from corrupting
the tty1 interface. Those messages remain available in the journal.

Progress is atomically persisted as root-only mode 0600 in
`/var/lib/beam-appliance/firstboot-state.json`. The system profile is stored in
`/etc/beam-appliance/config.json`. The completion marker is written last, after
keyboard, locale, timezone, maintenance account, configuration, Manager
synchronization and HTTP health verification. An interruption therefore
resumes the last verified stage.

Every GUI action failure is caught without closing the window. The user sees a
localized retry/back message while journald receives the checkpoint stage,
action name, exception type and traceback. Exception logging never includes
password values; passwords remain transient and are sent only to `chpasswd`
through anonymous stdin.

The screens are: bilingual language choice; country/region; keyboard preset;
free keyboard test and confirmation/change; locale and valid IANA timezone;
maintenance username/password/confirmation; configuration wait; final Manager,
LAN URL, one-time Web pairing code and BeamMP state. The code is generated by
the Manager identity, stored mode 0600, required for the first Web admin and
deleted after successful use. France, United Kingdom and United States presets are
supported, with four principal US timezones.

The keyboard is applied to console and X11 before any password input. The
password is validated and sent only over an anonymous stdin pipe to `chpasswd`;
it is never passed in argv, persisted, sent to the Manager or logged. The
maintenance account is separate from `beammanager` and `beammpserver`. Direct
root login is locked and SSH root login is denied.

LAN detection selects the global IPv4 on the lowest-metric default-route
interface, excluding loopback and common container/bridge interfaces. It falls
back to a usable UP global interface. Setup can complete without DHCP; the
status service retries detection every five seconds.

Gate 3 does not remove XFCE. The recommended candidate architecture is
headless: the normal product is browser-managed, while tty2 and SSH retain
recovery. Headless reduces idle RAM, installed size, boot work, update surface
and desktop maintenance. Retaining XFCE is justified only if local graphical
diagnosis becomes an explicitly supported workflow.
